# 快速执行层：参考成熟机器人，保留用户钱包签名

状态：部分已实施；新增 DEX/卖出/私有广播适配仍是待确认和验证的方案。

## 现状与约束

输入按 USDT 计价，5% 滑点上限，不默认无限授权，不保管私钥。一次明确的交易意图
只能领取和发送一次；未知结果必须查原单，不能自动再次花钱。速度目标需分别衡量
账户读取、余额检查、报价、安全模拟、等待用户、广播、链上确认及跨链结算，不能用
一个总加载框隐藏耗时，也不承诺链上或钱包端固定秒数。

当前买入使用 Relay 安全验证过的存入合约，即使同链也走 solver 结算，并不是直接
调用 PancakeSwap/Four.meme。后者可能减少同链环节，但需要独立的合约地址白名单、
调用数据解码、买卖税/内外盘状态、金额和最低到账验证，不能直接绕开现有安全检查。

## 目标流程

```text
全局账户 → 唯一链/合约 → 同链资金与市场状态 → 报价及模拟 → 用户签名
                           └ 无同链可用资金 → 跨链候选 + AI 复核 ─┘
用户签名 → 单次广播 → 持久哈希 → 源链确认 → 目标币到账 / 原单退款核对
```

买入、卖出、兑换应共享执行状态机，但请求必须显式区分方向、输入金额、输出合约及
收款人。跨链不能由 AI 编写 calldata 或接管签名；AI 只选已通过硬校验的候选 ID。

## 已实施

- 全站连接恢复与并行读取账户/网络，已授权钱包不重复弹授权。
- 目标链原生币余额优先，成功后不等其他链；同链路线不做额外 AI 跨链评审。
- 签名前并行只读余额、燃料费、模拟检查；不并发签名。
- 后端每个工作线程复用有界 HTTPS 连接池，禁用自动重试；不缓存余额用于签名。
- 钱包等待、哈希返回、确认、结算分别展示；无哈希不能标记已提交。
- 交易哈希先本地保存，后台报告不阻塞确认查询；防重领取仍在签名前持久化。

## 尚需适配和验证

1. BSC 原生同链路由：区分内盘/外盘，Four.meme 与 PancakeSwap 接口逐一解码验证。
2. 卖出与普通兑换：精确授权复用、买卖税/可卖性、原生币燃料保留及金额上限。
3. 私有 RPC/防 MEV：用户钱包是否支持由用户选择的广播通道必须核实；
   `eth_sendTransaction` 的实际签名和广播由插件控制，不能声称应用能接管它。
4. 慢节点只读切换与重复签名隔离：相同已签原始交易的重广播和重新生成交易不同，
   未拿到原始签名数据时不能凭超时自动重发。
5. 逐阶段错误码与计时诊断；更细的插件内部错误须由钱包暴露，不能从等待状态猜测。

## 方案权衡

优先保留插件钱包：不增加密钥托管风险，但用户确认和插件/MPC 延迟不受应用控制。
直接 DEX 适配可减少同链结算环节，但增加协议维护和合约安全验证成本。
不采用导入主钱包私钥或放宽滑点换速度，也不承诺无条件最快成交。

Maestro 的条款明确提到机器人需要私钥访问，因此它的签名边界不能原样照搬。
Banana Gun 官方说明强调现货交易与 MEV 防护，DBot 文档区分滑点定义并警告过高
滑点；这些应作为接口和风险设计参考，不是把营销速度当作本项目实测。
