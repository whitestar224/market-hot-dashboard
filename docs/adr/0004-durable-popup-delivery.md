# ADR-0004: 可恢复的本机播报投递

## Status
Accepted — 用户已要求解决播报漏报审计发现的问题。

## Context
旧实现先写去重，再放入内存队列；启动子进程被当作投递成功。失败、重启、队列满、45 秒超龄、泛标题去重均可造成漏报。左侧同位置叠放必须保留。

## Decision
使用本机 SQLite 持久化 outbox，不增加云服务或 AI 调用。

采集 → 精确事件去重 + 持久化入队 → 优先级调度 → 窗口可见回执 → 未读记录 → 用户确认已读。

- 接纳与去重同一数据库事务；旧记录仅兼容精确身份，不重播历史。
- 起窗不代表显示；子进程通过本地数据库和单次令牌上报实际可见时长。被遮挡暂停自动关闭计时；至少实际显示 4 秒才允许下一条覆盖。
- 未显示失败最多尝试 3 次、指数退避；超时和重启可恢复；原始期限不续期。过期/失败仍留未读记录，不当作实时机会重播。
- 内存仅维护最多 8 个窗口。回收窗口前必须确认最少可见时间，记录保留且不标已读。数据库待播报不因低优先级到达而挤掉关键消息。
- 默认普通消息队列时效 10 分钟，关键交易信号 3 分钟；实时事件流继续采用独立的原有机会窗口。
- 数据源分别运行在固定线程中，同源不重入；失败接纳不提交上游 seen。保留首次基线静默和无价值内容过滤。
- 未读列表仅本机/管理员可访问，同源校验；不暴露投递令牌、钱包或授权，不重发交易。
- 根据用户追加要求，删除事件流来源分类入口，默认单条合并流；未读/过期投递记录折叠在同一页，不另建页面。

## Consequences

### Positive
崩溃恢复、失败可追踪、突发队列不静默丢弃；显示和已读分离，不把启动成功夸大为用户已经看到。

### Negative
无法证明人的注意力；极端拥塞或系统桌面不可用时仍可能错过交易窗口，但原因和原始消息保留。强制崩溃在可见回执前可能导致一次重复（at least once）。

### Neutral
保留旧 seen 文件不修改；仅适用于部署后被本系统实际接纳的消息，无法恢复以前被丢掉且没有内容的记录。SQLite 不保留私钥，不更改买卖逻辑。

## Alternatives Considered
只增加队列长度无法解决回执和重启。引入云队列增加维护成本。全面改成常驻 GUI 进程影响现有确认/剔除/翻译行为，本次不采用。

## Verification plan
1. 临时数据库测试：接纳原子性、精确去重、重启恢复、租约、重试耗尽、原始过期时间和优先级突发。
2. 假进程测试：启动即退出、无回执、窗口回收、旧回执拒绝；不调用真实钱包或发送测试消息。
3. 前端与接口测试：未读分页、已读持久化、请求边界和安全文本渲染。
4. 回归测试和服务正常重启，检查健康接口、新页面与队列状态。
